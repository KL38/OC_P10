Lecture d'ensemble : sur les 40 questions chiffré + bruité + mixte de l'agrégat, l'enrichi est quasi partout en vert — la baseline n'avait aucune réponse chiffrée correcte (recall 0.0 systématique). Les échecs se concentrent sur 4 fronts, détaillés ci-dessous : routing texte→SQL, dérivation « par match », retrieval mixte, et garde-fou hors-couverture.

4.Cas instructifs : le coupable et la raison

Le socle chiffré · num_top_rebounds & consorts ✅ la démonstration du brief

« Quel joueur a capté le plus de rebonds ? » · sql · réf. : Ivica Zubac 1008
F 0.56→1.00 · CP 0.00→1.00 · CR 0.00→1.00

SELECT p.name, p.reb FROM players p ORDER BY p.reb DESC LIMIT 1 → Zubac 1008, exact. C'est l'échec emblématique de la baseline (le RAG texte répondait à côté sur les rebonds) : recall 0.0 → 1.0. Le même schéma se répète sur toute la catégorie simple_chiffre (ctx_precision 1.000) et complexe_chiffre — y compris les nouveaux tops/ordinaux (2ᵉ marqueur, 3ᵉ rebondeur) et les agrégats d'équipe. La robustesse au bruit orthographique (bruite : ctx_precision 0.90) est gratuite avec un LLM là où un parseur classique casserait.

Q2 · txt_reggie_miller ❌ la régression texte la plus nette (erreur de routing)

« Première option offensive la plus efficace de l'histoire des playoffs ? » · attendu rag · obtenu sql
F 1.00→0.20 · AR 0.83→0.68 · CP 1.00→0.00 · CR 1.00→0.00

Constat : la baseline répondait parfaitement (Reggie Miller, via le RAG). L'agent enrichi a jugé la question « chiffrée » et l'a envoyée au SQL : SELECT p.name, p.ts_pct … ORDER BY p.ts_pct DESC LIMIT 1 → Alondes Williams, TS% 125.0 (un joueur à 1 match, valeur aberrante).

Coupable : le routing de l'agent. « Efficace / la plus efficace » a des allures de métrique chiffrée ; le docstring du tool SQL a happé la question. Le modèle a même flairé l'anomalie (« semble anormalement élevé et probablement incorrect ») — mais a quand même livré la réponse. Faithful à un contexte faux : F 0.20 parce que la synthèse a nuancé, mais la preuve texte a totalement disparu (CP/CR 0).

💡 Solution : durcir la frontière de routing dans les docstrings/instructions — « efficacité, débat, opinion, histoire » relèvent du RAG, pas du SQL ; réserver le SQL aux totaux/classements de cette saison. À valider sur de nouvelles questions ambiguës.

Q9 · txt_reggie_allstar ❌ même cause, autre symptôme

« Combien de fois Reggie Miller a-t-il été All-Star ? » · attendu rag · obtenu sql
F 0.62→1.00 · AR 0.86→0.00 · CP 1.00→0.00 · CR 1.00→0.00

Constat : « Combien de fois » a déclenché le SQL : SELECT COUNT(*) FROM players WHERE name = 'Reggie Miller' → 0 (Miller est retraité, absent de la base 2024-25). L'agent a alors honnêtement répondu « information non disponible ». Mais la réponse (5 fois) EST dans le corpus Reddit — la baseline l'avait trouvée (CP/CR 1.0). Le refus est correct vu la table, mais c'est le mauvais outil : le RAG aurait répondu.

La leçon : le juge punit le refus (relevancy 0.00) alors que le faithfulness monte à 1.0 (fidèle au « 0 rows »). Une question factuelle sur une personne peut être texte ou chiffrée — ici le mot « combien » a sur-déclenché le SQL.

Q30 · num_sga_ppg ❌ le cas « dérivable » raté — l'ironie du run

« Combien de points par match SGA marque-t-il en moyenne ? » · sql · réf. : ~32,7 (2485 / 76)
F 0.67→0.00 · CP 1.00→0.00 · CR 1.00→0.00

C'était notre contre-exemple de la règle de granularité : « par match » = total ÷ gp, donc répondable. L'enrichi le rate spectaculairement. SQL généré : SELECT p.min_per_game * p.pts / NULLIF(p.gp, 0)… — il multiplie par les minutes (34,2 × 2485 / 76 = 1118,25), un non-sens dimensionnel. Puis la synthèse annonce « 25,4 points par match » — un troisième chiffre, ni celui du SQL ni le bon.

Coupables en cascade : génération SQL (composition ratée : elle confond « points par match » avec un produit de colonnes) et synthèse de l'agent (qui invente 25,4 sans lien avec le résultat 1118). Le petit modèle échoue sur la dérivation arithmétique, pas sur le lookup. Ironie : la baseline, elle, répondait via le chunk Excel aplati (F 0.67, CR 1.0).

💡 Solution : few-shot explicite « moyenne par match = pts * 1.0 / gp » + modèle de génération SQL plus capable sur la composition arithmétique. (reco #2)

Q54 · mix_edwards ⚠️ la difficulté propre au mixte : le retrieval de la moitié texte

« Que disent les fans d'Anthony Edwards en playoffs, et combien de points cette saison ? » · both
F 0.30→1.00 · CP 0.00→0.00 · CR 0.00→0.50

L'agent a bien appelé les deux outils (routing both — le comportement visé). Moitié chiffrée parfaite (2180 points). Mais la moitié texte a échoué : le tool RAG a remonté des chunks du thread « efficacité de Reggie Miller » au lieu du thread « équipes impressionnantes », et l'agent a honnêtement conclu « les discussions ne mentionnent pas directement Anthony Edwards ». D'où ctx_precision 0 : la moitié SQL prouve le chiffre, mais aucun contexte ne prouve l'opinion.

Pourquoi la ctx_precision mixte reste basse (0.23) partout : RAGAS évalue chaque contexte isolément contre une référence composée (texte + chiffre) ; au mieux la moitié des contextes matche. C'est une limite de mesure autant qu'un vrai déficit de retrieval texte sur corpus OCR bruité.

💡 Solution : mêmes leviers que la reco retrieval (nettoyage OCR, k plus large, re-ranking) ; côté éval, interpréter la ctx_precision mixte avec prudence.

Q55 · mix_siakam ❌ le risque résiduel : l'Excel aplati fuit dans le RAG

« Pourquoi Siakam est-il jugé sous-coté, et combien de points ? » · both · réf. : impact + 1576 pts
F 0.00→0.17 · CP 0.00→0.14 · CR 0.00→0.50

Chiffre correct (1576), mais le tool RAG a remonté un chunk de l'Excel aplati : « Analyse du top 15 des joueurs en nombre de points … NaN NaN NaN ». L'agent a alors brodé des raisons (« PIE, +/- sous-estimés… ») non ancrées dans un vrai commentaire de fan → faithfulness 0.17.

Coupable : le risque documenté au plan devenu réel — l'index FAISS contient encore les 202 chunks d'Excel aplati ; sur une question mixte mal ancrée, le retrieval texte retombe dessus. L'enrichi les court-circuite d'habitude par le routing chiffré→SQL, mais la moitié texte d'un mixte réexpose l'index complet.

💡 Solution : ré-indexer data/pdf seul (retirer l'Excel aplati de l'index texte) — le chiffré passe par SQL de toute façon. (reco #6, nouvelle)

hors_couverture · le garde-fou absent ❌ 10/10 routées SQL, 0 refus fiable

10 questions hors périmètre (attendu : refus) · toutes parties en SQL
faithfulness catégorie 0.20 → 0.52 · mais « faithful » ne veut pas dire « honnête »

Aucune n'est refusée d'emblée : l'agent génère une requête et habille le résultat. Un spectre de gravité :

• Hallucination pure — oob_height : requête sur les rebonds, puis invente « Ivica Zubac, 2,16 m (7 pieds 1 pouce) » depuis les poids du modèle (la taille n'est pas dans la base).
• Confabulation par ré-étiquetage — oob_playoffs : requête saison régulière Denver → « Jokić 2072 points en playoffs » ; oob_streak : MAX(wins) (victoires de saison) présenté comme une « série de 64 victoires » ; oob_last5 / oob_month : totaux saison ré-étiquetés « 5 derniers matchs » / « décembre ».
• Refus honnête (minoritaire) — oob_salary (« pas accès aux salaires ») et oob_vs_opponent (« ne permettent pas… uniquement contre les Lakers »).

Coupable : responsabilité de périmètre non assignée (défaut de design confirmé sur 10 cas). Le générateur SQL n'a aucun droit de refus — il doit produire quelque chose. RAGAS est aveugle : plusieurs de ces réponses fausses obtiennent faithfulness 1.0 (fidèles à un contexte SQL lui-même hors-sujet) — validation magistrale de l'exclusion de hors_couverture de l'agrégat.

💡 Solution (reco prioritaire, désormais chiffrée sur 10 cas) : garde-fou de périmètre dans les instructions de l'agent — « règle de granularité + exception dérivable » (refuser détail par-match / sous-période / domicile-extérieur / adversaire / donnée absente ; autoriser « par match » = total ÷ gp). À valider sur de nouvelles questions des deux côtés de la frontière.

Q5 · txt_randle_revelation ✅ l'effet du verbatim (reco #1), et sa limite

« Quel joueur des Timberwolves est décrit comme une révélation… ? » · rag · réf. : Julius Randle
F 0.12→1.00 · AR 0.92→0.98 · CP 0.00→0.00 · CR 0.00→0.00

Effet positif du verbatim : la question part mot pour mot au tool RAG (reco #1 appliquée). L'agent répond Julius Randle et cite le passage réel : « Randle has been a revelation. His bully ball has worked perfectly… » → faithfulness 0.12 → 1.00. Le verbatim a rétabli l'ancrage de génération.

Sa limite : ctx_precision/recall restent à 0. Le passage cité était bien dans l'un des 5 chunks, mais le juge ne le crédite pas — les chunks OCR sont si bruités (fragments r/nba mêlés, pseudos, timestamps) que la métrique de contexte ne reconnaît pas la correspondance. Le verbatim corrige la reformulation, pas la qualité d'ingestion.

💡 Solution : le levier restant est l'ingestion (nettoyage du texte OCR, re-chunking) — orthogonal au verbatim. (reco #7)

5.Leçons transverses

1. Faithfulness ≠ justesse (Q30, hors_couverture) — la métrique mesure la fidélité de la réponse au contexte, pas la vérité du contexte. Une chaîne peut être « fidèle à un contexte faux » (Alondes Williams TS 125, oob confabulés). D'où le faisceau des 4 métriques + références vérifiées.
2. RAGAS punit les refus corrects (Q9, hors_couverture) — relevancy 0 quand le système dit honnêtement « indisponible », scores flatteurs quand il confabule avec aplomb. → hors_couverture hors agrégat + jugement qualitatif.
3. Le routing est le nouveau point de fragilité (Q2, Q9) — la branche RAG est figée, mais un mot (« efficace », « combien ») peut sur-déclencher le SQL et détruire une réponse que la baseline réussissait. La qualité dépend désormais de la frontière de routing autant que des outils eux-mêmes.
4. Le text-to-SQL échoue par composition, pas par syntaxe (Q30) — lookups et agrégats simples fiables ; la dérivation arithmétique (points par match) et les compositions à deux étages produisent du SQL plausible et faux.
5. L'index mixte reste un risque (Q55) — l'Excel aplati vit encore dans FAISS ; le routing chiffré→SQL le court-circuite, mais la moitié texte d'une question mixte peut retomber dessus. Séparer les index est la parade propre.
6. L'observabilité a rendu chaque diagnostic possible — SQL généré, args des tool calls, routing : chaque « coupable » de ce rapport a été lu dans les predictions et les traces Logfire, span par span.

7.Limites du comparatif

  • Juge mistral-small-2506 (contrainte free tier) : scores indicatifs ; le delta est le signal, pas les valeurs absolues. Plusieurs réponses hors_couverture fausses obtiennent faithfulness 1.0.
  • Run unique, routing non déterministe (température 0.1 ≠ 0) : le routing observé est cohérent mais pas garanti reproductible — deux questions texte ont basculé en SQL sur ce run.
  • Catégorie mixte généreuse envers l'enrichi par construction : la baseline ne peut pas répondre à la moitié chiffrée (pas de SQL), donc son delta est structurellement gonflé. Incluse dans l'agrégat mais à lire avec ce biais en tête ; sa ctx_precision basse (0.23) est en partie un artefact de mesure (référence composée).
  • Corpus texte OCR bruité : les chunks issus des PDF scannés dégradent les métriques de contexte même quand la réponse est correcte (Q5) — plafond d'ingestion, pas de génération.
  • n = 10 par catégorie : bien plus robuste que les 2-4 du run précédent, mais lire les lignes autant que les agrégats.
