4.Chaque déviation expliquée : le coupable et la raison

Q1 · txt_impressive_duo ❌ la régression la plus instructive

« Quel duo de l'Orlando Magic les fans encensent-ils ? » · attendu rag · obtenu rag
F 0.80→0.00 · AR 0.90→0.86 · CP 0→0 · CR 1.00→0.00

Constat : réponse correcte (Wagner + Banchero), mais la preuve est absente des contextes récupérés.

Coupable : la reformulation de l'agent. Vérifié dans Logfire : le tool RAG a reçu "duo Orlando Magic fans encensent" — la question compressée en mots-clés. Rien de perdu sémantiquement, mais l'embedding d'une liste de mots-clés ≠ celui d'une question : le retrieval devient plat (scores FAISS 75.8 / 74.2 / 74.1 / 74.0 / 73.7 — aucun chunk ne se détache, 4/5 viennent du mauvais thread).

D'où vient la bonne réponse alors ? Des poids du modèle — violation de « fonde ta réponse uniquement sur les outils ». Le faithfulness 0.0 est un vrai positif : réponse juste sans preuve = même mécanisme que la confabulation de Q15, le dé est juste tombé du bon côté.

💡 Solution : transmettre la question utilisateur verbatim au tool RAG (1 ligne dans la docstring du tool). (reco #1)

Q4 · txt_homecourt_analogy ❌ déjà KO en baseline — et le recall 1.0 est un faux positif du juge

« Quelle équipe de NHL a joué à l'extérieur avant la finale ? » · rag · réf. : les Oilers (3 tours à l'extérieur avant la finale)
F 0.25→0.33 · AR 0.85→0.00 · CP 0→0 · CR 1.00→1.00 (à tort)

Constat : réponse fausse (« jamais arrivé ») — et, inspection des chunks à l'appui (traces), la vraie preuve n'est pas dans les contextes. Le seul passage « Oilers » récupéré est un encart r/hockey disant qu'ils ont l'avantage de la glace en finale — pas qu'ils ont joué les trois tours précédents à l'extérieur (l'affirmation de la référence). Le chunk où le fan fait l'analogie n'a pas été remonté.

Coupables en cascade : ① le retrieval — signature plate à nouveau (79.4 / 79.1 / 78.8 / 78.0 / 77.7, dont 2 chunks hors sujet) : le bon passage n'est pas remonté ; ② la génération — a répondu « jamais arrivé » en lisant le fil NBA voisin (« Never happened… ») : confusion de périmètre NBA/NHL ; ③ le juge — recall 1.0 à tort, sur les deux runs : il a crédité la référence sur la simple co-occurrence Oilers / finale / avantage, sans vérifier l'affirmation précise. Les métriques contexte de mistral-small sont laxistes face au paraphrasé proche.

Leçon : un score de métrique n'est pas une preuve — la localisation d'une panne exige la lecture des données brutes : ce recall 1.0 aurait fait conclure, à tort, que le retrieval était sain.

Relevancy 0.00 probablement aggravée par l'artefact {"question": ...} (cf. Q2).

💡 Solution : deux leviers côté retrieval — améliorer l'ingestion (l'OCR des PDF scannés produit des chunks très bruités qui dégradent les embeddings : nettoyage du texte OCR, re-chunking) et/ou élargir la recherche (k > 5, re-ranking) pour faire remonter le passage clé. Côté génération, un modèle plus attentif au cadre (NBA vs NHL) aiderait. Le recall 1.0 fantôme, lui, relève du juge (§ Limites) — aucune retouche du système ne le corrige.

Q6 · num_best_3pct ❌

« Meilleur % à 3 points (minimum 200 tentatives) ? » · sql · réf. : LaVine 44.6 %
F 0.00→0.50 · AR 0.90→0.95 · CP 0→0 · CR 0→0

Constat : le filtre est dans la question, la règle dans le prompt, le pattern dans le few-shot (fta >= 300)… et la requête générée n'a pas de WHERE → Alondes Williams, 100 % (volume infime).

Coupable : la génération SQL — vérifié dans Logfire : le tool a reçu "Quel joueur a le meilleur pourcentage à 3 points (minimum 200 tentatives) cette saison régulière NBA ?" — la reformulation est innocente (le filtre a survécu, la question a même été enrichie du cadre temporel). C'est le générateur SQL qui a ignoré « minimum 200 tentatives » malgré la règle explicite du prompt et le few-shot fta >= 300 qui montre exactement ce pattern : l'exemple ne suffit pas à garantir le transfert. Demi-point : le modèle a flairé l'anomalie (« semble anormalement élevé ») — l'instinct était bon, la requête non.

💡 Solution : modèle plus capable pour la génération SQL — le few-shot existait déjà et la consigne explicite a quand même été ignorée : c'est l'instruction-following du petit modèle qui plafonne, pas le prompt. (reco #2)

Q11 · num_team_total_rebounds ⚠️ refus propre, puni par le juge

« Total des rebonds des joueurs d'Oklahoma City (OKC) ? » · sql · réf. : 3660
F 0.10→1.00 · AR 0.97→0.00 · CP 0→1.00 · CR 0→0

Coupable : la génération SQL — WHERE t.name = 'Oklahoma City' alors que le nom exact est Oklahoma City Thunder → somme sur ensemble vide → NULL. Ironique : la question fournissait le code OKC ; team_code = 'OKC' suffisait.

Le point clé : l'agent a répondu « information non disponible » — exactement le comportement demandé (ne pas inventer)… et le juge le sanctionne : relevancy 0.00. RAGAS punit les refus corrects. Sans cette ligne, le −0.04 global d'answer_relevancy disparaît quasiment.

💡 Solution : préférer team_code quand un code est fourni, et mapper vers les valeurs exactes de teams.name sinon — l'utilisateur peut employer n'importe quel surnom (« OKC », « le Thunder », « Oklahoma »…), le prompt doit rendre ce mapping explicite. (reco #3)

Q12 · num_top10_points_sum ❌ le cas d'école du run

« Somme des points des 10 meilleurs marqueurs ? » · sql · réf. : 19 931
F 0.63→1.00 · AR 0.00→0.95 · CP 0→1.00 · CR 0→0.00

Le film : 1ʳᵉ requête SUM(pts) … ORDER BY pts LIMIT 10 → rejetée par PostgreSQL (GroupingError : on ne trie pas ce qui est agrégé en une ligne). La boucle Pydantic AI renvoie l'erreur au modèle, qui réessaie seul : SUM(p.pts) OVER () — window function syntaxiquement valide… qui somme les 569 joueurs (280 015) au lieu des 10 meilleurs. Réponse auto-incohérente : « 280 015 points » suivi de la liste des 10 joueurs dont la somme fait visiblement ~20 000.

Coupables en cascade : la génération SQL (le pattern « agrégat d'un top-N » exige une sous-requête — absent des few-shots, composition à deux étages, faiblesse typique des petits modèles), la boucle de retry, qui a retransformé l'échec bruyant en erreur silencieuse, et la synthèse de l'agent, qui a livré une réponse auto-incohérente — 280 015 annoncé juste au-dessus d'une liste de 10 joueurs qui somme visiblement ~20 000 — sans tiquer.

La leçon en or : faithfulness 1.0 sur une réponse fausse. La réponse est parfaitement fidèle à un contexte qui est lui-même faux — faithfulness mesure l'ancrage, pas la vérité. Seul context_recall (comparé à la référence) l'attrape.

💡 Solution : triple levier — few-shot agrégat-sur-sous-requête, meilleur modèle de génération SQL (la composition est la marche des petits modèles), et meilleur modèle d'agent pour la synthèse : un sanity check minimal (la somme annoncée vs la liste affichée juste en dessous) suffisait à repérer la contradiction. (reco #2)

Q15 · oob_last5 ❌ le mode d'échec le plus dangereux

« Meilleur % à 3 pts sur les 5 derniers matchs ? » · attendu : refus (donnée inexistante) · obtenu : sql
F 0.18→0.67 · AR 0.00→0.95 · CP 1.00→0.00 · CR 0→1.00

Constat : la base n'a aucun détail par match. Le modèle a généré une requête saison (filtre fg3a >= 200 correct !) et présenté le résultat comme « sur les 5 derniers matchs » — donnée vraie, étiquette fausse, aplomb total. Du maquillage de cadre : ni refus, ni chiffre inventé — une réinterprétation silencieuse de la question.

Coupable : une responsabilité de cohérence non assignée — défaut de design, pas d'un seul maillon. Le prompt SQL dit « Génère UNE requête répondant à la question » : le générateur n'a aucun droit de refus, il est structurellement obligé de produire quelque chose — ici il a silencieusement abandonné « 5 derniers matchs ». Puis la synthèse a rhabillé le résultat saison en « 5 derniers matchs ». Dans l'architecture actuelle, aucun étage n'est chargé de détecter qu'une question sort du schéma — même mécanisme qu'en Q16.

RAGAS est aveugle (relevancy 0.95, recall 1.0 contre une référence qui dit… que la donnée n'existe pas) : validation magistrale de l'exclusion de hors_couverture de l'agrégat.

💡 Solution : garde-fou de périmètre dans les instructions de l'agent — règle de granularité (refuser toute question exigeant le détail de matchs précis : sous-période, date, domicile/extérieur, adversaire) avec l'exception dérivable (« par match » = total ÷ gp : répondable).

Q16 · oob_home_away ❌

« Compare les rebonds domicile / extérieur » · attendu : refus · obtenu : sql
F 0.00→1.00 · AR 0.90→0.90 · CP 0→0 · CR 0→0

Constat : le modèle a inventé une liste d'équipes « à domicile » dans le SQL lui-même : CASE WHEN team_code IN ('BOS','GSW','LAL','LAC','PHX')… — hallucination structurelle.

Coupable : le même défaut de design qu'en Q15 (responsabilité hors-couverture non assignée) — le générateur SQL, sans droit de refus, va cette fois jusqu'à fabriquer une sémantique inexistante (la liste d'équipes « domicile » inventée). La synthèse a, elle, signalé l'incohérence (« valeurs inversées ou incomplètes… ») mais a quand même livré les chiffres. Demi-point pour l'instinct de doute.

💡 Solution : même garde-fou qu'en Q15 — l'agent refuse avant d'appeler le tool : le générateur n'est plus jamais exposé au hors-schéma, la fabrication disparaît. (reco #4 ; accessoirement #2.)

5.Leçons transverses

1. Faithfulness ≠ justesse (Q12) — la métrique mesure la fidélité de la réponse au contexte, pas la vérité du contexte. Une chaîne peut être « fidèle à un contexte faux ». D'où le faisceau des 4 métriques + références vérifiées.
2. RAGAS punit les refus corrects (Q11, Q15, Q16) — relevancy 0 quand le système dit honnêtement « indisponible », scores flatteurs quand il confabule avec aplomb. → hors_couverture hors agrégat + jugement qualitatif : décision de Phase 2 doublement validée.
3. La reformulation de l'agent est un facteur de variance du retrieval (Q1 — innocentée en Q6, vérifié dans les traces : le filtre avait survécu à la reformulation) — le retriever est figé, mais la requête qui y entre ne l'est plus. Tout maillon LLM intercalé déplace le comportement des maillons suivants.
4. Échec bruyant > échec silencieux (Q12, et l'inverse en Q11) — PostgreSQL strict, validation Pydantic, rôle SELECT-only : tout ce qui refuse fort vaut mieux que tout ce qui devine. Le retry automatique peut retransformer un échec bruyant en erreur silencieuse.
5. Le text-to-SQL échoue par composition, pas par syntaxe (Q12, Q16) — requêtes plates fiables ; compositions (agrégat-sur-top-N) et demandes hors schéma produisent du SQL plausible et faux. La marche est sémantique.
6. L'observabilité a rendu chaque diagnostic possible — reformulations (args des tool calls), SQL généré, scores FAISS : chaque « coupable » de ce rapport a été identifié dans une trace Logfire, span par span.

7.Limites du comparatif

  • Juge mistral-small-2506 (contrainte free tier) : scores indicatifs ; le delta est le signal, pas les valeurs absolues. Exemple concret : le recall 1.0 de Q4 est un faux positif (référence créditée sur une co-occurrence Oilers/finale/avantage, alors que l'affirmation précise est absente des chunks) — détecté uniquement par lecture des contextes bruts.
  • Run unique, routing non déterministe (température 0.1 ≠ 0) : le routing observé (12 sql / 4 rag) est cohérent mais pas garanti reproductible à l'identique.
  • n = 16 : les moyennes par catégorie reposent sur 2 à 4 questions — lire les lignes, pas seulement les agrégats.
  • Artefact {"question": ...} dans 2 réponses texte (adaptateur OpenAI-compat) : cosmétique mais pénalise probablement la relevancy de Q4.
